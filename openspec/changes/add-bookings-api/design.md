# Design

## Context

Гарантия «ровно одна активная бронь» должна держаться при гонках и опираться на БД. Схема — в `add-data-model-and-seeding` (`bookings.active_slot_id` UNIQUE).

## Goals / Non-Goals

**Goals:** корректные статусы; гарантия на уровне БД; понятные сообщения; простой код для объяснения.

**Non-Goals:** авторизация, идемпотентность POST по ключу, очереди.

## Decisions

### Поток `POST /api/bookings`

1. `StoreBookingRequest` валидирует поля (в том числе `exists:slots,id`) → 422.
2. `BookingService::create(Slot $slot, string $name, string $email)`:
   - если `$slot->starts_at <= now()` → `SlotUnavailableException` (причина: past) → 409;
   - `Booking::create([... 'active_slot_id' => $slot->id])` внутри `try`;
   - `catch (UniqueConstraintViolationException)` → `SlotUnavailableException` (причина: taken) → 409.
3. Контроллер отвечает `201 {"data": {"id": ...}}`.

- **Почему так, а не `exists()` + insert или `lockForUpdate()`:** между проверкой и вставкой есть окно гонки; в SQLite нет блокировок строк. UNIQUE-индекс срабатывает атомарно в самой БД на любом из трёх СУБД. `exists()` перед вставкой можно оставить для быстрого понятного 409, но решающей является вставка.
- **Ловим именно `Illuminate\Database\UniqueConstraintViolationException`** (наличие в выбранной версии Laravel проверить при реализации), а не общий `QueryException`: иначе другие ошибки БД выглядели бы как конфликт слота. Проверить при реализации, что для FK-ошибки он не срабатывает.
- **Гонка вокруг времени** (слот стал прошедшим между проверкой и вставкой) допустима: бронь создаётся для слота, который начался в пределах миллисекунд.

### Поток `DELETE /api/bookings/{id}`

- Атомарный условный апдейт: `Booking::whereKey($id)->whereNull('cancelled_at')->update(['cancelled_at' => now(), 'active_slot_id' => null])`. Затронута 1 строка → 204.
- Затронуто 0 строк: если бронь с таким ID существует (`exists`), она уже отменена → 404 «Бронь уже отменена»; иначе → 404 «Бронь не найдена».
- Решение владельца: повторная отмена возвращает 404 (ТЗ допускает 204 или 404), а различие повторной отмены и неизвестного ID передаётся сообщением в теле. Условный апдейт делает отмену корректной и при двух одновременных DELETE: только один получит 204.
- Отмена брони уже начавшегося слота не запрещается (слот остаётся `past`); специального бизнес-правила в ТЗ нет — допущение, указать в README.

### Сообщения

- `Этот слот уже занят` / `Этот слот уже прошёл`; 422 использует стандартные сообщения Laravel (`APP_LOCALE=ru` требует языковых файлов `lang/ru/validation.php` — добавить, иначе сообщения будут английскими).

### Тестируемость

SQLite сериализует записи, поэтому настоящую параллельную гонку в тесте PHPUnit воспроизвести нельзя. Гарантию проверяют тест на 409 при повторном запросе и тест, что вторая активная вставка нарушает индекс (опционально).

## Risks / Trade-offs

- `active_slot_id` должен поддерживаться только сервисом — риск рассинхрона при прямых правках БД.
- Повтор POST после сетевого сбоя, когда первый запрос уже создал бронь, вернёт 409; frontend обновляет список и показывает актуальное состояние.
