# Design

## Context

- Сервер: `'customer_email' => ['required', 'email', 'max:255']`; `email` без параметров = режим RFC (egulias/email-validator).
- Клиент: `const EMAIL_RE = /^[^\s@]+@[^\s@]+\.[^\s@]+$/` в `BookingDialog.vue`.
- Таблица расхождений — в `proposal.md`.

## Decisions

### Рекомендуется: та же регулярка на сервере

```php
// Тот же формат, что проверяет форма (BookingDialog.vue, EMAIL_RE): точка в домене, без пробелов.
private const EMAIL_FORMAT = '/^[^\s@]+@[^\s@]+\.[^\s@]+$/u';

'customer_email' => ['required', 'email', 'regex:'.self::EMAIL_FORMAT, 'max:255'],
```

Сообщение: `'customer_email.regex' => 'Укажите корректный email.'` — тот же текст, что у `email` и на клиенте.
Флаг `u`, чтобы `[^\s@]` работал с кириллицей посимвольно. В Vue у `EMAIL_RE` комментарий со ссылкой на `StoreBookingRequest`.

Почему так: множество адресов, которые принимает сервер (`email` ∩ регулярка), — подмножество того, что принимает браузер
(регулярка). Браузер никогда не отклоняет адрес, который прошёл бы на сервере; сервер остаётся последней проверкой, а его 422 уже
отображается под полем (требование `booking-ui` «Validation errors (422)»).

### Альтернатива: `email:filter`

Одно слово вместо регулярки, `a@b` отклоняется. Но `FILTER_VALIDATE_EMAIL` отклоняет `иван@пример.рф` и `ivan@пример.рф`, а
браузер их пропускает — расхождение просто переезжает в другую сторону, и теперь форма пускает адрес, который сервер всегда отвергает.

### Рассмотрено и отклонено

- Ослабить клиент до `required` + `type="email"` — форма с `novalidate`, браузерной проверки формата не будет вовсе, а ТЗ требует проверку в браузере.
- Один источник правила (отдавать регулярку с сервера) — лишняя связность ради одной строки.

## Risks / Trade-offs

Регулярка дублируется в двух местах (PHP и JS); при правке менять обе — отмечено комментариями с обеих сторон.

## Migration Plan

Backend + комментарий во frontend; откат — revert коммита. Существующие брони не проверяются заново.
