# Design

## Context

Frontend загружает расписание один раз и фильтрует по дате в браузере (разрешено ТЗ п. 4), поэтому серверная фильтрация не нужна.

## Goals / Non-Goals

**Goals:** минимальный и стабильный контракт; никаких ПДн; статус считается на сервере.

**Non-Goals:** пагинация, фильтры, кэширование.

## Decisions

- **Статус считает сервер**, один раз на `now()`, чтобы клиент не зависел от своих часов: `past` > `booked` > `available`.
- **`past` важнее `booked`.** Слот, который уже начался, нельзя забронировать или освободить для брони, поэтому клиенту достаточно одного значения `past`; `booking_id` остаётся для информации.
- **Формат ответа:** `{"data": [...], "meta": {...}}` в стиле Laravel API Resources. `meta.timezone` нужен, потому что ISO-строка содержит смещение, но не имя пояса; frontend использует имя для `Intl.DateTimeFormat`.
- **Возвращаются все слоты**, включая слоты прошедших дней (после повторных запусков Seeder). Для демо данных мало; пагинацию не вводим — зафиксировано в README как ограничение.
- **Реализация:** `Slot::with('activeBooking')->orderBy('starts_at')->get()` + `SlotResource`; время сравнивается как Carbon.
- **Пример ответа:**

```json
{
  "data": [
    {"id": 1, "starts_at": "2026-11-16T09:00:00+03:00", "ends_at": "2026-11-16T10:00:00+03:00",
     "status": "past", "booking_id": null},
    {"id": 6, "starts_at": "2026-11-16T14:00:00+03:00", "ends_at": "2026-11-16T15:00:00+03:00",
     "status": "booked", "booking_id": 12}
  ],
  "meta": {"timezone": "Europe/Moscow", "server_time": "2026-11-16T13:41:10+03:00"}
}
```

## Risks / Trade-offs

- Рост числа слотов без пагинации — приемлемо для демо.
- Расхождение часов клиента и сервера не влияет на статус, так как он считается на сервере; кратковременное устаревание списка устраняется обновлением после 409.
